Birthday Memory Security and API Testing Guide

A beginner-friendly guide for running this application, testing its API in Postman, finding security weaknesses safely, reviewing GitHub and Docker configuration, and asking useful questions about the code.

Use this guide only on your own local copy. Do not test a system, account, database, or API that you do not own or have explicit permission to assess. The examples below are designed for localhost and test data.

2. Run the application locally

Open the project directory. 
cd /Users/hvaandres/Documents/GitHub/cyber-uvu-student-projects/cybr-4550/threat_actors/birthday_memory
Install dependencies. 
npm run install:all
Create the server environment file. 
cp server/.env.example server/.env

PowerShell: Copy-Item server\.env.example server\.env

Start Docker Desktop.

On macOS or Windows, open Docker Desktop and wait until it reports that the engine is running.

docker info
npm run db:up
docker compose ps
Optionally load sample records. 
npm --prefix server run seed
Start the API and frontend. 
npm run dev

Open http://localhost:5173.

If you see failed to connect to the docker API, Docker Desktop is not running. If Vite reports ECONNREFUSED for /api/birthdays, the frontend is running but the API could not connect to PostgreSQL.

Verify the API:

curl -i http://localhost:4000/api/health

Stop the app with Ctrl+C, then stop PostgreSQL with:

npm run db:down

4. Postman: beginner setup

  1. Install and open Postman.
  2. Create a new collection named Birthday Memory Local Tests.
  3. Create an environment named Birthday Memory Local.
  4. Add a variable named baseUrl with value http://localhost:4000.
  5. Select that environment in the upper-right corner.
  6. Use {{baseUrl}} in request URLs so you can change hosts later.
Start by sending the health request. If it fails, fix Docker/PostgreSQL/API startup before testing other requests.

Scenario A: GET health

  1. Create a request named Health check.
  2. Choose method GET.
  3. Enter {{baseUrl}}/api/health.
  4. Click Send.
  5. Expect status 200 OK and JSON containing "status":"ok".

Scenario B: GET all birthdays

  1. Create a GET request for {{baseUrl}}/api/birthdays.
  2. Click Send.
  3. Expect a JSON array. If you ran the seed command, it should contain sample records.
  4. Try the query parameter q=Ada in the Params tab.
  5. Try month=12 to filter by December.

Scenario C: POST a new birthday

  1. Create a POST request for {{baseUrl}}/api/birthdays.
  2. Open Body → raw and select JSON.
  3. Use this test payload:
{
  "firstName": "Postman",
  "lastName": "Tester",
  "birthdate": "1995-06-15",
  "phone": "+1 555 123 4567",
  "email": "postman@example.com"
}
  1. Send the request.
  2. Expect 201 Created.
  3. Copy the returned id. Save it as a Postman environment variable named birthdayId.
The ID is needed for the PUT and DELETE scenarios.

Scenario D: PUT an existing birthday

  1. Create a PUT request for {{baseUrl}}/api/birthdays/{{birthdayId}}.
  2. Choose Body → raw → JSON.
  3. Use this complete replacement payload:
{
  "firstName": "Updated",
  "lastName": "Tester",
  "birthdate": "1995-06-20",
  "phone": "",
  "email": "updated@example.com"
}
  1. Send the request.
  2. Expect 200 OK and verify that the returned values changed.

Scenario E: DELETE an existing birthday

  1. Create a DELETE request for {{baseUrl}}/api/birthdays/{{birthdayId}}.
  2. Send it without a request body.
  3. Expect 204 No Content.
  4. Send the GET-all request again and verify the test record is gone.

Scenario F: validation tests

For each case, use the POST request and change the JSON body:

Test body changeExpected result
Remove firstName422 with an errors.firstName message
Use "birthdate": "not-a-date"422 with a birthdate error
Use "birthdate": "2099-01-01"422 because future dates are rejected
Use "email": "not-an-email"422 with an email error
Use a nonexistent UUID in PUT/DELETE404, not a database stack trace

5. Safe vulnerability checks

These are learning checks, not instructions to attack an external system.

Authentication and authorization

Ask whether a user must log in before reading, creating, editing, or deleting records. In the current local code, the routes do not show authentication middleware. Test with Postman without an Authorization header and document the result.

  • Can an unauthenticated user send GET?
  • Can an unauthenticated user send POST?
  • Can an unauthenticated user send PUT or DELETE?
  • Can one user access another user's records?

Potential issue: without authentication and ownership checks, anyone who can reach this API may be able to access or change all birthday data.

CORS

server/src/index.js currently uses app.use(cors()). Inspect the response:

curl -i -H "Origin: http://example.test" http://localhost:4000/api/birthdays

Look for Access-Control-Allow-Origin. An unrestricted value may be acceptable for a local demo, but production applications should allow only trusted frontend origins.

SQL injection safety

The routes use PostgreSQL parameters such as $1, which is the correct pattern. Use harmless search text containing quote characters:

curl -G http://localhost:4000/api/birthdays \
  --data-urlencode "q=' OR '1'='1"

The input should be treated as search text. Do not use destructive payloads or test against databases you do not own.

HTML/script injection

Create a local test record with text such as <b>Test</b>. In the React UI it should display as text, not execute or become unexpected markup. Search for dangerous rendering APIs:

grep -RInE 'dangerouslySetInnerHTML|innerHTML|eval\(|new Function' \
  client server --exclude-dir=node_modules

Error disclosure

Send malformed JSON in Postman and check that the response does not reveal stack traces, passwords, connection strings, or private filesystem paths. Pay particular attention to the health endpoint, which currently includes a database error message when the database query fails.

Database exposure

The Compose file publishes PostgreSQL on host port 5544 and uses simple development credentials. That is convenient locally but should not be exposed to the public internet. Check:

docker compose ps
docker port thebirthdates-db
git ls-files .env server/.env

Environment files should not be tracked. Never commit real credentials.

Database TLS

When PGSSL=true, the code uses rejectUnauthorized: false. This encrypts the connection but disables certificate verification. For production, use the database provider's trusted CA/certificate configuration instead.

6. GitHub security features

  1. Push the project to a private GitHub repository while learning.
  2. Open Settings → Security → Advanced Security.
  3. Enable Dependabot alerts and Dependabot security updates.
  4. Enable Secret scanning and push protection if available for the repository.
  5. Add a GitHub Actions workflow using CodeQL for JavaScript analysis.
  6. Review pull requests for dependency updates and security findings before merging.

Before enabling features on a real repository, confirm the repository's privacy, organization, and billing settings. Do not upload secrets to test scanning.

Example CodeQL workflow

Create .github/workflows/codeql.yml using GitHub's current CodeQL starter workflow for JavaScript/TypeScript. The workflow should initialize CodeQL, build if needed, and run the analysis on pushes and pull requests. Use GitHub's generated workflow rather than copying an old action version.

7. Snyk dependency and container checks

Snyk can scan both application dependencies and container images. Use it only with code and images you are authorized to inspect.

  1. Create an account at snyk.io or install the Snyk CLI.
  2. Authenticate the CLI with snyk auth.
  3. From the project directory, scan the root dependencies:
snyk test
snyk test --file=server/package.json
snyk test --file=client/package.json
  1. Review severity, exploitability, affected package, and fixed version.
  2. Run a monitored scan only if you want the project stored in your authorized Snyk account:
snyk monitor --file=server/package.json
snyk monitor --file=client/package.json

For Docker, first create an application image with an explicit Dockerfile. Then scan it:

docker build -t birthday-memory-api:local ./server
snyk container test birthday-memory-api:local

This repository's Compose file currently runs a PostgreSQL image rather than building the Node API into an image. Scan the exact image tag used in your environment and review the PostgreSQL image's official security updates.

8. Understand the Docker image and container

Image: a packaged filesystem and metadata used to create containers. Container: a running instance of an image.

docker compose config
docker image ls
docker ps
docker inspect thebirthdates-db
docker compose logs postgres

Ask these questions:

  • Which image and version are used?
  • Which ports are published to the host?
  • Which environment variables contain credentials?
  • Is a persistent volume attached?
  • Does the health check verify the service is ready?
  • Is the container running as a non-root user where appropriate?
  • Are only required ports and capabilities exposed?
  • Are images pinned to a trustworthy, maintained tag or digest?

For this project, the named volume preserves database data. Running docker compose down -v removes that volume, so use it only when you intend to delete local test data.

9. Beginner prompts for understanding the code

Use these prompts with an AI assistant while including only code you are allowed to share:

Understand the architecture

“Explain this project as a request flow from the React form to the Express route to PostgreSQL and back. Name each file involved and explain what data changes at each step.”

Understand the server

“Explain server/src/index.js line by line as a beginner. Identify middleware, route registration, startup behavior, error handling, and what happens if PostgreSQL is unavailable.”

Understand the database

“Explain server/src/db.js. Show how environment variables become a PostgreSQL connection, how the schema is created, why indexes exist, and which values must never be committed.”

Understand each API route

“For every route in server/src/routes.js, explain the method, URL, input, SQL operation, success status, failure statuses, and whether authentication or authorization is enforced.”

Review validation

“Compare the validation in the React form with server/src/validate.js. Identify checks that exist only in the browser and explain why server-side validation is required.”

Review for vulnerabilities

“Perform a defensive code review of this local Express/React/PostgreSQL project. Report only concrete, reproducible findings with file, line range, severity, impact, confidence, safe local reproduction, and minimal remediation. Do not provide destructive payloads.”

Review the Docker setup

“Review this Docker Compose configuration for secrets, exposed ports, image pinning, health checks, persistence, privileges, network exposure, and production risks. Separate development conveniences from vulnerabilities.”

Learn a finding

“Teach me this finding as a beginner: what is the vulnerable behavior, why does it matter, how can I reproduce it only on localhost, how would I fix it, and how would I test the fix?”
