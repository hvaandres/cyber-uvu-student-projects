CYBR 4550 · Threat Actors · Applied Security Assessment

🕯️ Operation Candlelight: Someone Left the Front Door Open

We shipped an application that stores real people's names, birthdates, phone numbers, and email addresses — and we never added a single line of authentication. You are the security engineer we just hired. Find out how bad it is, or fix it. Then defend your work in front of the board.

⏱ Est. time: 5- 10 hours, depending on how good you are with investigations 📶 Difficulty: Advanced 🧭 You choose your track 💼 Portfolio deliverable 🎤 Oral defense required

⚠️ Read This First — Rules of Engagement

This section is not boilerplate. Violating it is an academic integrity issue and, depending on what you touch, a criminal one.

Authorized scope — and nothing else:

  • Permitted: Your own fork of this project, running on your own machine, bound to localhost / 127.0.0.1, with data you seeded.
  • Permitted: Containers you built yourself, on your own Docker daemon.
  • Forbidden: The instructor's repository, any classmate's machine or fork, any UVU network host, any cloud instance you do not personally own, and any third-party service.
  • Forbidden: Seeding the database with real personal information about real people. Use synthetic data only — fake names, fake numbers, fake emails. Do not use your own or your family's real data, because your screenshots go into a public portfolio.
  • Forbidden: Exposing your instance to the internet (no ngrok, no port forwarding, no public cloud deploy) while it is in its vulnerable state.

Safety rails for the offensive track: denial-of-service testing is limited to demonstrating the conditions that make DoS possible (for example, an unbounded query or a missing rate limit) plus small, controlled proof requests. Do not run sustained volumetric attacks, even against yourself — a resource-exhaustion screenshot is worth the same credit and will not cook your laptop.

If at any point you are unsure whether something is in scope, the answer is: ask before you run it. "I wasn't sure so I tried it" is the exact sentence that ends security careers.

📨 The Situation

Internal Memo — Confidential

From: Office of the CISO
To: Incoming Security Engineer
Re: Birthday Memory — pre-launch security posture

Engineering built Birthday Memory to solve a small internal problem: remembering teammates' birthdays. It is a React front end, an Express API, and a PostgreSQL database. It works. People like it. Leadership now wants to roll it out company-wide and eventually to customers.

Here is my problem. The team built the entire thing on localhost, where everything is trusted by default, and they never went back. There is no login screen. There is no API key. There is no authorization check of any kind. Every endpoint that reads, writes, modifies, or deletes personal records is reachable by anyone who can send an HTTP request.

The database credentials appear to be committed to the repository. The container configuration was written for convenience, not for safety. I do not believe anyone has ever run a vulnerability scan against this stack.

I need to know two things before this ships: can this be broken into, and what does it cost us if it is? The board meets at the end of the term. Your report goes in front of them. Be thorough, be accurate, and be ready to be questioned.

The data at risk is not trivial. Full name plus date of birth plus phone plus email is a complete identity-theft starter kit and a social-engineering pretext generator. Treat this as the PII breach it would be, not as "just birthdays."

🔎 What We Already Suspect (Your Starting Scope)

This is a scope statement, not an answer key. It tells you which surfaces are in bounds. It does not tell you what is actually exploitable, how severe it is, or whether the item is even a real finding. Determining that is the assignment.

Three domains are in scope

🔌 Domain 1 — The API

Express app in server/src/. Look at index.js (middleware, CORS, error handling, health endpoint) and routes.js (every CRUD route and what does — or does not — gate it).

🗄️ Domain 2 — The Database

PostgreSQL connection and schema in server/src/db.js. Consider credentials, connection defaults, transport security, privilege level, and what is stored in plaintext.

🐳 Domain 3 — The Container

docker-compose.yml, the image it pulls, what it publishes to the host, how secrets reach the container, and what the runtime is permitted to do.

Open for the specific questions we want answered about the API
  • What identity does the API require before it will read, create, modify, or delete a personal record? What happens if a request supplies no identity at all?
  • Which origins is a browser permitted to make credentialed calls from? How was that decided, and by what line of code?
  • How many records can a single unauthenticated request retrieve? Is there any ceiling, page size, or throttle?
  • What response headers does the API set to protect a browser client? Compare against a baseline like Helmet's defaults.
  • When something fails internally, how much does the response tell the caller about the internals?
  • Is there any record of who performed a destructive action, and when? If a thousand records vanished tonight, what would the investigation have to work with?
Open for the specific questions we want answered about the database
  • Where do the database credentials come from when no environment file is present? Trace it in code and state the actual values.
  • Are those same values discoverable by someone who only has read access to the public repository?
  • Is the database reachable from anywhere other than the application container? From the host? From another machine on the same Wi-Fi?
  • When TLS is enabled for the database connection, is the server's certificate actually verified? What attack does the current setting permit?
  • What privilege level does the application's database role hold? Does the app need everything that role can do?
  • Is the PII encrypted at rest, in transit, or in backups? Can you read it straight off the volume?
Open for the specific questions we want answered about the container
  • Which user does the process inside the container run as? What does that mean if the process is compromised?
  • Is the base image pinned to something immutable, or to a tag that can change underneath you? What supply-chain risk does that create?
  • How do secrets get into the container, and who can read them back out afterward with standard Docker commands?
  • Which ports are published to the host interface, and does every one of them need to be?
  • What Linux capabilities, filesystem permissions, and resource limits does the container have? What is the blast radius of a container escape?
  • How many known CVEs are in the image as pulled today? Prove it with a scanner rather than asserting it.

🧠 A deliberate trap — read carefully

At least one "obvious" vulnerability class that you will be tempted to report is probably not present in this codebase, because the developers happened to do that one thing correctly. If you report it anyway without testing it, you will have submitted a false positive to a board of directors. In this assignment, an unverified finding costs you more points than a missed one. Test first. Report what you proved.

🎯 Learning Objectives

By completing this assignment, you will be able to:

  • Conduct a scoped security assessment of a multi-tier application using a recognized methodology (OWASP WSTG, PTES, or NIST SP 800-115).
  • Distinguish a proven vulnerability from a suspected one, and document the difference honestly.
  • Score findings with CVSS v3.1 and defend each metric choice in the vector string.
  • Translate a technical defect into business risk that a non-technical executive can act on.
  • Apply defense-in-depth across three distinct layers — application, data, and container runtime — rather than patching a single symptom.
  • Produce written work that survives hostile review, and defend it verbally under questioning.

TRACK A ⚔️ Red Team — Full Requirements

A1. Pick a methodology and follow it

Ad hoc poking is not an assessment. Select one framework, state it in your report, and structure your testing around it:

  • OWASP Web Security Testing Guide (WSTG) — recommended; maps cleanly to a web API.
  • PTES — if you want the full engagement lifecycle framing.
  • NIST SP 800-115 — if you want the formal technical-assessment structure.

A2. Required coverage

Your testing must cover all three in-scope domains and explicitly address every category below. For each one you must state a verdict: Confirmed Vulnerable, Not Vulnerable (tested), or Not Tested (with justification). Silence on a category is treated as incomplete coverage.

Required category list (OWASP Top 10 2021 alignment)
  • A01 Broken Access Control — can an unauthenticated party read, create, alter, or destroy records? Demonstrate each verb separately.
  • A02 Cryptographic Failures — PII at rest, PII in transit, certificate validation behavior.
  • A03 Injection — test it properly, then report the truth (see the trap warning above).
  • A04 Insecure Design — what was never designed in at all, as opposed to implemented badly?
  • A05 Security Misconfiguration — CORS policy, security headers, default credentials, error verbosity, exposed services.
  • A06 Vulnerable and Outdated Components — dependency and image CVEs, with scanner output.
  • A07 Identification and Authentication Failures — characterize the total absence of an authentication layer as a finding in its own right.
  • A08 Software and Data Integrity Failures — image tag mutability, lockfile integrity, absence of an SBOM.
  • A09 Logging and Monitoring Failures — destroy a record, then demonstrate what forensic trail exists. This is one of the strongest board-level findings available to you; do not skip it.
  • A10 SSRF — assess and report, even if the verdict is "not applicable, here is why."
  • Container-specific — runtime user, capabilities, secret retrieval via standard Docker commands, host port exposure, image CVE count, data readable directly off the volume.
  • Availability — identify unbounded operations and missing throttles. Demonstrate the condition, not a sustained flood.

A3. Evidence standard — this is where grades are won and lost

Every finding requires all six of the following. A finding missing any element receives partial credit at best:

  1. Reproduction steps — numbered, deterministic, and complete enough that the instructor can reproduce it on a clean clone without asking you anything.
  2. Raw evidence — the actual request and the actual response. Full curl -i output, Burp/ZAP captures, or terminal transcripts. Not a paraphrase.
  3. Visual proof — a screenshot with a visible timestamp and, where relevant, the tool's own output pane. Redact anything sensitive.
  4. CVSS v3.1 score with the full vector string — e.g. AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:N — plus one sentence justifying each metric you chose. Expect to be asked why you picked PR:N over PR:L.
  5. Business impact — what it costs the organization in plain English. Regulatory exposure, notification obligations, reputational damage, operational disruption.
  6. Remediation recommendation — specific and actionable. "Add authentication" is not a recommendation. Name the mechanism, the layer it belongs in, and the trade-off it introduces.

Negative results are graded. A professional report documents what you tested and found secure, not only what broke. It is how the reader knows the scope was actually covered. Include a "Tested — Not Vulnerable" section, and expect it to be read closely.

A4. Suggested tooling

You are not required to use all of these, but you must justify your toolchain in the report.

  • Interception and fuzzing: Burp Suite Community, OWASP ZAP, curl, httpie, Postman
  • Surface discovery: nmap (localhost only), ffuf or gobuster for endpoint enumeration
  • Dependency and image scanning: npm audit, Trivy, Grype, Docker Scout, Syft for SBOM generation
  • Container benchmarking: Docker Bench for Security, CIS Docker Benchmark
  • Static analysis: Semgrep, njsscan, GitHub CodeQL
  • Secret discovery: gitleaks, TruffleHog — run these against your fork's history, not just its current state
  • Database: psql, or any client, to test reachability and privilege

A5. Deliverables

  • The board report (format specified in the shared section below).
  • A security/ directory in your fork containing your evidence files, scanner output, and any proof-of-concept scripts you wrote.
  • A findings register as a structured file (findings.md or CSV) with ID, title, severity, CVSS vector, affected component, and status.
  • Your portfolio README.md.

TRACK B 🛡️ Application Security — Full Requirements

B1. Threat model before you touch code

Engineers who patch before they model fix symptoms. Produce, in this order:

  • A data flow diagram showing browser, API, and database, with trust boundaries drawn explicitly. Mermaid, draw.io, or clean hand-drawn-and-scanned are all acceptable.
  • A STRIDE analysis (Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege) across each boundary you drew.
  • An asset inventory: what data exists, how sensitive it is, and what regulation might attach to it.
  • A prioritized remediation roadmap ranking every issue by risk, with your ranking criteria stated. You must justify why the top item outranks the second.

B2. Remediate all three domains in code

Your fix must be real, committed, and runnable. A document describing what you would have done does not satisfy this.

Domain 1 — API hardening requirements
  • Authentication. Implement a real mechanism (session-based, JWT with sane expiry and rotation, or API keys with proper storage). Document why you chose it over the alternatives — you will be asked.
  • Authorization. Authentication answers "who are you." Authorization answers "may you do this to this record." Implement both; explain the difference in your report.
  • CORS. Replace the permissive policy with an explicit origin allowlist, and explain the interaction between CORS and credentialed requests.
  • Security headers. Apply a hardened baseline. State what each header you enabled actually defends against — do not just import a library and move on.
  • Rate limiting and throttling on every mutating route and on bulk reads.
  • Pagination and result caps so no single request can drain the table.
  • Input validation hardening beyond the current checks, plus an explicit output-encoding position for stored values.
  • Error handling. Generic responses to clients, detailed logs server-side. Eliminate internal detail leakage.
  • Audit logging. Every create, update, and delete must produce a durable record of actor, action, target, and timestamp. Show a sample log line for a deletion.
Domain 2 — Database hardening requirements
  • Eliminate credential exposure. Remove hardcoded and committed credentials everywhere they appear, including code defaults. Then check the Git history — deleting a secret from the working tree does not remove it from the repository.
  • Secrets management. Move to a defensible mechanism (Docker secrets, environment injection from a vault, or an equivalent). Document the rotation story: what happens the day a credential leaks?
  • Least privilege. Create a dedicated application role with the minimum grants required. Demonstrate that the app still works and that the role cannot do more than it needs.
  • Transport security. Enable TLS with real certificate verification. Explain the specific attack that the previous setting allowed.
  • Network exposure. Ensure the database is reachable only by the services that need it.
  • Protection of PII at rest. Choose an approach — column-level encryption, full-disk/volume encryption, tokenization — implement or concretely specify it, and honestly state its limits.
  • Backup and recovery posture, including whether backups inherit the same protections as the live data.
  • Optional distinction: row-level security policies.
Domain 3 — Container hardening requirements
  • Write a hardened Dockerfile for the application: multi-stage build, minimal base image, a pinned immutable base reference, a non-root USER, no secrets baked into any layer, and a HEALTHCHECK.
  • Add a .dockerignore and explain which sensitive paths it keeps out of the build context and why that matters.
  • Harden the Compose configuration: stop publishing internal services to the host, apply read_only where viable, drop unnecessary capabilities, set no-new-privileges, and impose CPU and memory limits.
  • Scan and prove it. Produce before-and-after vulnerability scan output for your images and quantify the reduction. A number beats an adjective.
  • Generate an SBOM and explain to the board, in one paragraph, why anyone should care.
  • Distinction: a CI pipeline (GitHub Actions) that runs dependency audit, secret scanning, and image scanning on every push, and fails the build on high-severity findings.

B3. Verification standard — this is where grades are won and lost

For every fix, supply paired before-and-after evidence. Asserting that something is fixed earns nothing.

  • Before: the request that succeeded when it should not have, with its response.
  • After: the same request now rejected, with the correct status code — and a matching authorized request that still succeeds, proving you secured the app instead of breaking it.
  • Automated tests that encode the security property, so a future developer cannot silently regress it.
  • Scanner deltas with counts before and after.
  • A residual risk statement. Nothing is ever fully secure. State what you did not fix, why, and what compensating control covers it. Boards trust engineers who name their remaining risk; they distrust engineers who claim total victory.

B4. Suggested tooling and references

  • Standards: OWASP ASVS (declare your target level and justify it), OWASP Cheat Sheet Series, CIS Benchmarks
  • Libraries: Helmet, express-rate-limit, zod or joi, argon2 or bcrypt, pino for structured logging
  • Scanning: npm audit, Snyk, Trivy, Grype, Semgrep, gitleaks, Syft
  • Verification: Vitest or Jest with Supertest for security regression tests

B5. Deliverables

  • The board report (format specified in the shared section below).
  • A working, hardened application in your fork — it must still run.
  • Your threat model artifacts, committed to the repository.
  • Security regression tests plus instructions to run them.
  • A SECURITY.md documenting the resulting security posture and the vulnerability disclosure process.
  • Your portfolio README.md.

📄 The Board Report (Both Tracks)

Your report is the primary deliverable. It goes to a board of directors — a mixed audience of executives who control budget and technical leaders who will check your work. Write for both.

Required structure

  1. Cover page — title, your name, date, classification marking, document version.
  2. Executive summary (1 page, hard limit) — no jargon, no CVEs, no code. A board member must be able to read only this page and know what the risk is, what it could cost, and what decision you need from them. Write this last.
  3. Scope and methodology — what was in scope, what was out, which framework you followed, which tools you used, and the limitations of your assessment. Stating your limitations increases your credibility; hiding them destroys it when someone finds them.
  4. Findings or remediations — the technical core, ordered by risk, each meeting the evidence or verification standard for your track.
  5. Risk analysis — likelihood, impact, and a risk matrix. Connect technical severity to business consequence.
  6. Regulatory and compliance considerations — identify which frameworks plausibly apply to this data (consider GDPR, CCPA/CPRA, state breach-notification law, PCI DSS if payments were ever added, and any sector-specific rules). Name them accurately; do not invent applicability. Getting this wrong in front of a board is memorable for the wrong reasons.
  7. Recommendations and roadmap — prioritized, with rough effort estimates and a proposed sequence. Distinguish "stop the bleeding this week" from "architectural work next quarter."
  8. Conclusion — your professional opinion. Should this ship? Take a position and own it.
  9. Appendices — raw tool output, full transcripts, extended screenshots, references.

Format requirements

  • PDF, 12–25 pages excluding appendices.
  • Page numbers, consistent headings, and a table of contents.
  • Every figure and screenshot captioned and referenced from the body text.
  • Citations for any standard, CVE, or external source you rely on.
  • Proofread. Typos in a document that claims rigor undercut the claim.
  • The PDF must also be committed to your fork.
What separates a top report from an average one
  • It quantifies. "Approximately 4,200 PII records retrievable in a single unauthenticated request" lands; "sensitive data is exposed" does not.
  • It admits uncertainty precisely, rather than hiding it behind confident phrasing.
  • Its severity ratings are defensible line by line, not vibes rendered as colors.
  • It anticipates the obvious objection and answers it before it is raised.
  • It reads like it was written by one person with a point of view, not assembled from tool output.

Your report will be reviewed in detail, and you will sit for a 10–15 minute oral defense. The purpose is simple: confirm that you understand what you submitted. You may bring your report and your repository. Please take a look at the sample questions and record and answer all of them in a teams video, and share the link. Please create this video under the teams channel called Homework inside of the group "CYBR-4550-X01 | 2026 Fall - Full Term"

If you cannot explain a finding or a fix in your own words, it will not count toward your grade, regardless of how well it is written up.

Sample questions — Red Team track
  • Walk me through your highest-severity finding without looking at your notes.
  • You scored this Critical. Justify each metric in your CVSS vector. Why S:U and not S:C?
  • You reported this as exploitable. Show me, right now, on your machine.
  • Which category did you test and find secure? Why is the code correct there?
  • An engineer claims your top finding is not real because the app only runs internally. Respond.
  • If you had one week and one engineer, which single finding would you fix first, and what does that leave exposed?
  • What did you fail to test, and how might that omission have changed your conclusions?
Sample questions — Application Security track
  • You chose this authentication mechanism. What did you reject, and what does your choice cost you?
  • Explain the difference between what you implemented for authentication and what you implemented for authorization. Show me both in the code.
  • Your token expires in that window. Defend that number.
  • You removed the credential from the file. Is it gone from the repository? Prove it.
  • Your container runs as a non-root user. What specific attack does that stop, and what does it not stop?
  • Show me the test that fails if a future developer removes your authorization check.
  • What is your largest remaining risk after all of your fixes, and why did you accept it?
Questions either track may receive
  • Explain this to me as though I am the CFO and I do not know what an API is.
  • What is the realistic worst-case scenario if we ship as-is, and how likely is it?
  • Which regulations plausibly apply to this data, and what are our notification obligations after a breach?
  • You used an AI assistant somewhere in this work. Where, and how did you verify its output?
  • What surprised you most during this assessment?

📊 Grading Rubric (100 points)

Point distribution, what is assessed in each area, and the most common way students lose those points
Component Pts What earns full credit Most common point loss
Technical depth 30 All three domains covered at the required depth; work goes beyond the obvious surface issues. Only the API examined; database and container treated as afterthoughts.
Evidence / verification 25 Every claim backed by reproducible proof meeting the six-element standard (A) or paired before/after evidence (B). Assertions without artifacts; screenshots that do not show what the caption claims.
Report quality 20 Board-ready structure, accurate risk ratings, genuine business translation, clean professional prose. An executive summary crammed with jargon; severity ratings that cannot be defended.
Oral defense 15 Fluent, unscripted command of your own work; handles pushback without bluffing. Reading from the report; unable to explain a submitted finding or fix.
Portfolio & repo hygiene 10 Clean fork, meaningful commit history, strong README, nothing sensitive committed. One giant commit named "final"; a leaked .env or unredacted screenshot.

Adjustments

  • Deduction — false positives: up to −5 points per fabricated or unverified finding reported as confirmed. This is the single most damaging error in professional security work, and it is graded that way here.
  • Deduction — scope violation: testing anything outside your own fork and machine results in a zero and referral under the academic integrity policy.
  • Deduction — new exposure: committing a real secret or an unredacted credential to your public fork costs points even if the rest of the work is excellent.
  • Bonus — up to +5: an exceptional contribution such as a working CI security pipeline, a genuinely novel finding, a polished custom proof-of-concept tool, or a remediation demonstrably stronger than the standard fix.

⚖️ Academic Integrity & AI Use

AI assistants are permitted for this assignment. They are part of the modern security toolchain and pretending otherwise would be poor preparation. Three conditions apply:

  1. Disclose it. Include a short appendix stating which tools you used, for what, and how you validated the output.
  2. Verify everything. AI-generated findings are hypotheses, not evidence. An AI-invented CVE or hallucinated CVSS score in a board report is a false positive and will be graded as one.
  3. Own it. The oral defense is the equalizer. If you cannot explain it, you did not learn it, and it does not count.

Collaboration: discussing methodology, tools, and concepts with classmates is encouraged. Sharing report text, findings, evidence files, or code is not. Every submission must reflect your own testing on your own fork.

A closing note. The vulnerabilities in this application are not exotic. They are the ordinary consequence of a team building on localhost, where everything is trusted, and never revisiting that assumption before shipping. This is how the overwhelming majority of real breaches begin: not with a sophisticated adversary, but with a door nobody remembered to lock.

Whichever track you choose, the skill being assessed is the same one: the ability to look at working software and ask what happens when someone hostile uses it. That question does not have a tool. It has you.
